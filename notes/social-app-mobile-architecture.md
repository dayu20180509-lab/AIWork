# 社交 App 移动端技术架构：分层评审与 0→1 建议

> 针对「业务层 / 能力层 / 基础设施层 / 跨端层」四层图的评审，以及从 0 到 1 的可落地改法。

## 结论

**分层思维可用，原图不能直接照搬。**

保留「业务 → 能力 → 基建」的依赖方向，但需要：

1. 补上**领域服务层**（否则 Feed/IM/媒资逻辑会散落或污染能力层）
2. 把**跨端从「底层」改为「二期技术策略」**（避免依赖方向倒置）
3. 允许 **Feed / IM** 作为重同步垂直切片，而不是普通业务页
4. 用**模块依赖规则**约束边界，比再画一层更重要

## 原设计好在哪里

| 点 | 说明 |
|---|---|
| 业务与能力分离 | Feed / IM / 创作与网络 / 存储 / 埋点分开，方向正确 |
| 能力层「横切」意识 | 避免每个业务自己造网络与存储轮子 |
| 基建独立 | 崩溃、性能、监控单独成层，利于质量兜底 |
| 跨端标「二期」 | 0→1 不强行上跨端，时机意识是对的 |

## 原设计的主要问题

### 1. 跨端层不应作为最底层（高）

RN / SwiftUI / KMP 是**交付与复用策略**，不是业务与能力依赖的地基。

一期若双端原生，真正的底是系统能力与自研基建；把跨端画在最下，会暗示「上层都建立在 RN/KMP 之上」，依赖方向错误。

**改法：** 跨端不进依赖栈，单独标为「二期策略」，在领域 API 稳定后再接入。

### 2. 缺少领域服务层（高）

原图是：业务 UI → 通用能力。社交里大量逻辑介于两者之间：

- Feed 分页、增量、去重、已读
- IM 会话列表、消息序、ack、离线补偿
- 媒资：压缩、分片上传、转码状态、失败重试
- 关系：关注/粉丝、权限、主页聚合

这些若塞进业务页会复制；塞进「业务无关」能力层会污染边界。

**改法：** 增加「领域服务」层，对外稳定 API，对内可持有私有存储与同步引擎。

### 3. 「能力层业务无关」表述过强（中）

登录、推送、图片在社交场景都带语义：

| 模块 | 平台能力部分 | 领域部分 |
|---|---|---|
| 登录 | Token、刷新、安全存储 | 账号资料、绑定、风控态 |
| 推送 | 厂商通道、权限、点击拉起 | 路由到会话/Feed、未读聚合 |
| 图片 | 解码、缓存、显示 | 裁剪比、水印、上传策略、CDN |

**改法：** 能力层只保留真正平台化的部分；带业务规则的沉到领域服务。

### 4. 组件库与可观测性同层过粗（中）

- **组件库**：表现层基建，被业务 UI 直接依赖
- **崩溃 / 性能 / 监控**：运行时基建，横切全 App

可以仍叫「基建」，但对内分子域，依赖规则分开写清。

### 5. IM / Feed 被画成普通业务模块（中）

二者是**重同步垂直切片**：长连接、本地库、增量协议、冲突与补洞。应允许：

- 私有 DB / 同步引擎
- 独立线程与电量策略
- 对外只暴露领域 API 给 UI

而不是「业务页 + 通用 HTTP」。

### 6. 跨端三线并行等于未决策（低）

「RN + SwiftUI 渐进 + KMP 探索」同时出现，二期会变成三线试验。

**建议：** 0→1 锁双端原生；二期在 **RN（偏 UI 复用）** 与 **KMP（偏逻辑复用）** 中择一为主；SwiftUI 仅作 iOS UI 演进，不与另外两条抢同一边界。

## 建议分层（依赖自上而下）

```
┌─────────────────────────────────────────────────────────┐
│  L1  应用壳 / 导航                                       │
│      Tab · 路由 · 深链 · 登录门禁 · 全局弹层              │
├─────────────────────────────────────────────────────────┤
│  L2  业务模块（垂直切片）                                  │
│      Feed · 关系/主页 · 创作 · IM ·（可选）AI 对话        │
├─────────────────────────────────────────────────────────┤
│  L3  领域服务                                            │
│      Feed 同步 · 会话/消息 · 媒资管道 · 关系 · 账号会话   │
├─────────────────────────────────────────────────────────┤
│  L4  平台能力（尽量业务无关）                               │
│      HTTP/WS · 存储 · 图片/视频 SDK · 推送 · 埋点 · 配置  │
├─────────────────────────────────────────────────────────┤
│  L5  运行时 / 工程基建                                    │
│      组件库 · 崩溃 · 性能 · 日志 · DI/模块化 · 构建发布    │
└─────────────────────────────────────────────────────────┘

        ※ 跨端 = 二期策略（非 L6 地基）
          RN 业务页 或 KMP 领域逻辑（择一为主）
```

### 依赖规则（强制）

1. 上层可依赖下层；下层**禁止** import 业务模块
2. 业务模块之间**禁止**横向硬依赖；共享逻辑下沉 L3
3. IM / Feed 可有私有实现，但对外只暴露 L3 API
4. L4 保持稳定、可测试、可替换（便于二期跨端替换实现）
5. 跨端接入不得破坏已有领域契约

## 相对原图的模块归位

### 业务层保留并收紧

| 模块 | 一期建议 | 备注 |
|---|---|---|
| Feed | 必做 | 读流 + 互动；推荐可后置 |
| 个人主页 / 关系 | 必做 | 社交图核心 |
| 创作 | 必做 | 先图文，再短视频 |
| IM | 必做轻量 | 先私信/会话，音视频后置 |
| AI 对话 | 可选 | 除非产品核心，否则挂在聊天壳 + LLM 网关，勿与 Feed/IM 同等重投入 |

### 原能力层拆分

- **留在 L4：** 网络、通用 KV/DB 封装、图片解码缓存、推送通道、埋点 SDK、登录会话（token）
- **升到 L3：** 账号资料与绑定、推送业务路由、媒资上传状态机、Feed/IM 同步

### 原图建议补齐（一期）

- 长连接 / 实时通道
- 媒资上传与失败重试
- 远程配置 / 功能开关
- 深链与分享
- 权限与隐私合规入口
- 模块化与依赖治理（组件化、路由表、接口隔离）

## 0→1 分期

### 一期：验证核心社交环

**目标：** 双端原生（或一端先发）跑通「关注 → 消费 → 互动 → 私信」闭环。

**必须有：**

- 账号登录与会话
- 关系链 + 主页
- Feed 消费与赞评
- 图文创作发布
- 轻量 IM / 私信
- 推送、崩溃、核心埋点

**刻意推迟：** 完整音视频 IM、复杂推荐、跨端框架、重度 AI。

### 一期中后期：夯实同步与媒资

- 离线缓存与增量同步
- 上传断点 / 重试
- 短视频管道（若产品需要）
- 远程配置与性能基线
- 把重复逻辑收敛进 L3

### 二期：择一跨端

在 L3 API 稳定后：

- 要快铺业务页 → 偏 **RN**
- 要共享领域与同步逻辑 → 偏 **KMP**
- **SwiftUI** 只作为 iOS UI 现代化，不与上两者并行抢边界

## 工程形态建议（务实）

| 议题 | 0→1 建议 |
|---|---|
| iOS / Android | 独立工程 + 共享 OpenAPI / 错误码 / 埋点字典 |
| 模块化 | 按 L2/L3 分 module；能力用接口，实现可替换 |
| 数据 | Feed/IM 本地库与 UI 状态分离；先保证正确性再追求极致离线 |
| 质量 | 启动、Feed 首屏、发布成功率、IM 送达率、崩溃率进日报 |
| 团队 | 先垂直功能交付，再抽平台；过早平台化会拖慢验证 |

---

## 一页决策摘要

1. **原四层图：方向对，结构需改** — 加领域层，跨端移出依赖栈  
2. **0→1 锁定双端原生 + 共享契约** — 不要在一期并行 RN/KMP/SwiftUI  
3. **Feed / IM 按同步系统建** — 不是普通 CRUD 页面  
4. **能力层保持瘦** — 业务语义进领域服务  
5. **依赖规则 > 图层美观** — 没有规则的分层只是示意图
